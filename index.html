A generative UI study for travel

Answers becomeinterfaces.

An unofficial prototype where an agent assembles interactive travel views from a finite, data-bound component catalog.

The work asks a practical question: can one conversation produce the right interface for each travel decision?

Technical details

The model chooses a registered React tree. It does not write React code, query raw fare rows, or control the surrounding application.

  1. 1Prompt and compact contextCurrent artifacts, scope manifests, displayed facts and selected fare facts
  2. 2Codex model decisionCatalog, locations and four bounded tools
  3. 3Strict validationSchema, component names, references, ownership and size budgets
  4. 4Host executionTyped state updates and source-owned React rendering
  5. 5Bounded projectionsTyped slices from the 50-million-row synthetic SQLite fixture
  6. 6Local interactionControls update browser state without another model call

Input and context

The browser sends the visible message history plus a compact snapshot of the current artifacts, query scope, selected fare facts and immutable display records. Privacy checks reject normalized fare rows and other bulk-data keys before the request reaches the local agent.

Tools and model runtime

The agent exposes four tools: inspect_display, present, edit_artifact and create_artifact. A signed-in local Codex model receives their schemas, the registered catalog and bounded context, then returns explanatory text with at most one tool decision.

What a predefined component is

Each catalog entry is a source-owned React component with allowed scalar props, data bindings and child rules. TravelSurface is the required root. Layout components may receive agent-authored children. Leaf components keep their implementation fixed.

Composition and validation

The model selects component names and scalar references in JSON. Streaming prefixes are pruned while they arrive. The final tree is checked for registered names, allowlisted props, current artifact and dataset references, unique keys, booking ownership, depth, node count and byte limits. Invalid output gets one repair attempt.

Data and browser runtime

The full 50-million-row deterministic fixture stays in server-side SQLite. The Python API returns typed fare pages, calendar days, carrier facets, mode summaries and highlights. A page is capped at 100 rows. The browser caches bounded projections, manifests, pinned items and selected-trip state.

Host and agent ownership

The agent owns the registered composition and its scalar references. The host owns the chat shell, PlanningTracker, data queries, saved state, UI primitives and direct interactions. MultiCityPlanGrid is a fixed composite with its own per-leg controls. Full fare rows never enter model context or tool payloads.

Why this page is static

This GitHub Pages presentation documents the prototype. The working demo also needs the Python fare API, the Node agent, the SQLite fixture and a signed-in local Codex runtime.
