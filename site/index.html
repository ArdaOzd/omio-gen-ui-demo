Subcomponents

These 49 reusable subcomponents are used in the construction of the compositions above. Layouts arrange the interface; controls, data views and status displays provide its behavior. Controls share the chosen cities, dates and filters. The Python backend executes fixed SQL queries for fare results using those inputs. Route-aware labels follow the selected cities, and every block uses the same Wayfinder theme.

Layouts

11 subcomponents
Layouts: purposes and connections
SubcomponentPurpose and connections
TravelSurfaceFrame a composed travel scene and its child controls, views and summaries. The children connect to the same host-managed trip state, while the shared travel theme supplies the surface, spacing and typography.
CalloutPresent a short explanation, warning or travel note alongside other components. Its heading and body can use registered route text that follows the selected cities and stays, and it uses the common themed notice surface.
CarouselBrowse child panels horizontally with scroll snapping. Each panel keeps its own trip-state and fare-selection connection, while the shared theme supplies the surrounding presentation.
InlinePlace related controls or small views on one wrapping row. The shared theme sets the spacing, while each child keeps its connection to the current trip inputs as the available width changes.
ResponsiveGridArrange child components in a grid that adapts to the available width. Each control or view keeps its own state and query binding, allowing parallel comparisons within one composed scene.
SectionGroup related controls and views beneath an optional heading. Its children retain their existing trip-state and data connections, so a section can organize one leg or a whole planning task.
SplitPanePlace a primary view beside a supporting pane, such as filters or a summary. The layout positions its children; their shared trip state carries changes and selections between the panes.
StackArrange child components vertically with consistent spacing. Controls, fare results and summaries can share a column while keeping their own connections to the current trip.
StickySummaryKeep a child summary near the top of its scrolling container. A selected-itinerary or total view inside it still reads the shared selection state, so the pinned summary follows choices made elsewhere.
TabsSwitch between child views in an accessible tabbed panel, with keyboard navigation. Tab labels can resolve the current selected cities, while the active tab is local presentation state and each view keeps its data binding.
TravelHeroIntroduce the journey with a prominent heading and optional supporting content. Route-aware headings follow the selected cities, and the shared theme supplies the hero presentation.

Controls

15 subcomponents
Controls: purposes and connections
SubcomponentPurpose and connections
CarrierFilterChoose carriers from the available company names and matching-fare counts. The Python backend runs fixed carrier-facet SQL queries using the current travel scope, and each checkbox writes the shared carrier filter used by connected fare views.
CityFieldChoose a route leg’s origin and destination from city suggestions loaded from the location catalog. The Python backend reads that catalog with fixed SQL queries when the control loads; choosing a city stores its stable identifier in the shared route, so connected legs, labels and fare scopes follow the revised cities.
DateStripSet a departure date with a native date input. Changing this date updates the shared trip and shifts its leg windows, so connected fare views load the revised schedule.
DateWindowSet an inclusive start and end date with two native date inputs. Changes update the trip’s dates, prompt a coverage check and refresh connected fare requests.
DirectToggleLimit matching results to direct connections. Its checkbox updates the shared filter, which the host includes in connected fare and comparison requests.
DurationRangeSet an optional maximum journey duration in minutes. The typed duration filter narrows connected fare requests, and clearing the field removes the limit.
FareOrderChoose Departure, Cheapest or Fastest ordering for one route leg. It writes the leg’s sort state, which the connected fare list and calendar use when requesting their fixed results.
FarePickerChoose a fare from a compact dropdown with previous and next result pages. The Python backend runs fixed SQL queries using the shared route, dates, filters and ordering, and choosing an option synchronizes selection with other fare views.
ModeChipsInclude or exclude transport modes with pressed-state buttons; choosing none means all modes. It updates the selected leg’s mode filter, which connected fare views use when retrieving results.
PriceRangeSet an optional maximum fare in euros per passenger, stored as integer cents. The typed price filter is shared by connected fare requests, and clearing the field removes the limit.
SortSelectChoose price, duration or departure ordering in a native dropdown. It writes the trip-wide sort state for views that use that ordering; route-leg views can keep their separate FareOrder selection.
StayAllocationSet 0–30 nights for each configured destination, shown with readable city names. It writes the shared stays and shifts downstream leg windows, which combine with selected arrival times to constrain the next departures.
StayDurationSet a stay of 0–30 nights after the bound leg’s destination. The shared itinerary combines that stay with the selected arrival time to update the earliest departure for the next leg and its connected fare requests.
TransportSelectInclude or exclude the available transport modes for one route leg. Available choices come from the host’s fare-scope metadata, and the selection updates the leg’s shared filters so connected fare views refresh.
TravelDateSet the departure date for a route leg using the shared itinerary schedule. The first leg updates the trip dates; later legs adjust the stay after the preceding arrival, keeping downstream fare scopes connected.

Data views and summaries

17 subcomponents
Data views and summaries: purposes and connections
SubcomponentPurpose and connections
CheapestFastestShow the cheapest fare and fastest journey for the current route scope, with company and departure/arrival details. The Python backend runs fixed highlights SQL queries using the shared cities, dates and filters; either result can be added to or removed from the shared trip.
CitySequenceList the shared route’s stops in their configured order and show the planned nights at each destination. It reads city identifiers and stays from the same itinerary state used by the trip controls, formatting identifiers as readable city names.
ComparisonMatrixCompare transport modes by minimum fare, fastest duration and number of matching options. The Python backend runs fixed summary SQL queries using the current cities, dates and active filters, aggregating all matching fares in that scope.
ComparisonTableCompare individual fares in a table of mode, company, date, departure, duration and price. The Python backend runs fixed SQL queries using the shared travel inputs, providing ten results per page; each row connects to the shared fare selection.
CoverageSummaryExplain the route and date coverage of the loaded fare scopes, including completeness and the number of matching options. It reads the host’s saved coverage metadata for the current trip, alongside the same scope information used by fare controls and results.
DurationPricePlotCompare up to fifty matching fares as duration-versus-price points. The Python backend runs fixed SQL queries using the shared route, dates, filters and ordering. Clicking a point opens its exact route, company and departure/arrival details, with an action to add or remove that fare from the shared trip.
FadeFaresBrowse a leg’s selectable fares in a vertically scrolling list that loads further result pages. The Python backend runs fixed SQL queries for the current cities, date window, transport choices and arrival threshold; selections are shared with other fare views.
FareCalendarCompare available days for one route leg, then inspect and select fares for the active day. The Python backend runs fixed SQL queries using that leg’s shared dates, filters and preceding-arrival threshold. Choosing a date or fare updates the shared plan.
FareCardsShow selectable fare cards with company, departure, duration, route and price details. The Python backend runs fixed SQL queries using the shared route, dates, filters and ordering, while previous and next controls page through seven results at a time.
ItineraryTimelineShow departure date, time, route, duration and price in a journey list with shared Add/Remove actions. It requests up to five fallback fares through fixed SQL queries in the Python backend using the shared travel inputs, while preferring cached selected-fare facts for display when available.
ModeBreakdownShow how many matching fares are available for each transport mode. The Python backend runs fixed summary SQL queries using the current cities, dates and filters, so the counts update alongside connected fare views.
MultiCityPlanGridArrange every route leg into one planner with city, departure, transport, fare-order and fare controls, plus stays between legs. It reads the shared itinerary and delegates fare retrieval to fixed internal panels whose requests run predefined SQL in the Python backend, keeping changes connected across the plan.
PriceCalendarShow a date calendar with the cheapest representative fare and matching-option count for each available day. The Python backend runs fixed calendar SQL queries using the leg’s shared cities, filters and date window. Date selection and Add cheapest actions update the shared plan.
RouteMapDraw a schematic route connecting the shared itinerary’s cities in order. It reads the same city sequence as the trip controls and turns those identifiers into readable labels, so city edits update the diagram.
SelectedFareCountDisplay the number of fares currently selected in the shared trip. It subscribes directly to the shared selection state and updates as any connected fare view adds or removes an option.
SelectedItineraryList the fares already selected in the shared trip, including route, date, mode and per-passenger price. It reads cached selected-fare facts, so selections made in another fare view appear here without a separate result query.
SyntheticTotalShow the total cost of the fares selected in the shared trip. It sums the saved fare prices and applies the passenger count, updating as selections change in other views.

Status displays: purposes and connections
SubcomponentPurpose and connections
ArtifactSkeletonShow a themed placeholder while a travel scene is being prepared. It displays the supplied or default status text; the host decides when this status belongs in the composition.
CoverageNoticeExplain that some requested dates may lie outside the loaded fare coverage. It presents a supplied or default notice in the shared theme; coverage detection belongs to the host.

Technical details

The model proposes a small tree of registered components and live references. The browser validates it, renders source-owned React, and keeps data queries and interaction state outside the model.

System architecture

A bounded local loop

The browser sends the prompt and a compact snapshot to a local model agent. A validated scene returns to the catalog renderer, while a separate Python service supplies bounded projections from the server-side fare fixture.

Component connections

Registered pieces, fixed behavior

TravelSurface is the required root. The agent chooses registered layouts and leaves, while their React implementations, state updates, queries and selection behavior remain source-owned.

Root and layouts

Compose the page

TravelSurface is the required root for one artifact. Only registered layout nodes, including heroes, sections, stacks, grids, panes, tabs and carousels, accept composed children.

Controls

Update typed state

Date, route, mode, carrier, price, duration, direct-trip, sorting and stay controls write to the browser state store. They do not start another model turn.

Data views

Read bounded projections

FareCards, calendars, comparisons, timelines and CheapestFastest request fixed projection types. Selection-capable views send exact displayed fare references to the shared tracker.

Fixed composite

Own the complex workflow

MultiCityPlanGrid is one agent-visible leaf. React fixes each leg as CityField → TravelDate → TransportSelect → FareOrder → FadeFares, with StayDuration between legs.

Trip summaries

Reflect shared selections

SelectedItinerary, SyntheticTotal and SelectedFareCount read the current selected-fare state. StickySummary keeps that context visible beside longer result views.

Host shell

Keep conversation and selection stable

The chat runtime, display ledger and PlanningTracker sit outside the composed tree. They preserve what was shown, local interactions and selected fares across scene changes.

Runtime flow

Five controlled handoffs

Each boundary narrows what crosses it. The model makes the composition decision; the host executes everything that touches application state or fare data.

  1. 1
    Capture compact context

    The prompt travels with current artifacts, live references, selected bounded facts and a record of what the user saw.

  2. 2
    Choose a registered scene

    The model returns component names and scalar references, not React, HTML, CSS, SQL or fare rows.

  3. 3
    Validate before rendering

    The boundary checks registered names, allowlisted props, live references, ownership and strict size limits.

  4. 4
    Render and interact locally

    Source-owned React renders the scene. Direct controls update typed browser state without another model call.

  5. 5
    Request bounded data

    The coordinator asks the Python API for fixed projections. Selected displayed fares flow into the host-owned tracker.

Interactive without a live backend

These compositions run the source-owned React catalog directly in your browser. The full 1–15 December 2026 fare range is packaged as lazy-loaded static shards; no Python API, model agent, sign-in or live booking service runs on this page.
